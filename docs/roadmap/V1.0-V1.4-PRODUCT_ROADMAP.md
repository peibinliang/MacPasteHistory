# 粘易 V1.0 → V1.4 产品规划

> 项目：粘易 / MacPasteHistory  
> 规划范围：V1.0 → V1.4  
> 目标平台：macOS 14.0+  
> 技术基线：Swift 6、SwiftUI、AppKit、SQLite、Vision、Sparkle  
> 产品原则：本地优先、隐私优先、渐进增强、稳定优先、文档同步  
> 开发方式：Codex Agent + LOOP + TDD  
> 发布策略：每个版本里程碑完成后创建独立 Git Tag；正式 Release、签名、公证、Sparkle 包与 GitHub Release 由后续独立发布任务执行。

---

## 1. 产品定位

粘易当前已经具备文本与图片历史、时间线、结构化搜索、内容类型识别、开发者内容动作、OCR、自动粘贴、敏感内容过滤、DeepSeek AI 润色、Sparkle 更新与本地存储治理等能力。

后续不再把粘易仅定义为“剪贴板历史工具”，而是逐步演进为：

> **本地优先的 macOS 内容工作台。任何进入 Mac 剪贴板的临时内容，都能够被快速找到、整理、转换和再次使用。**

长期产品能力围绕六个方向演进：

```text
Capture
  ↓
History
  ↓
Search
  ↓
Organize
  ↓
Transform
  ↓
Reuse / Workflow
```

最终能力体系：

```text
粘易

│   └── Source App

├── Search

├── Organize
```

# 3. V1.0.x —— 核心稳定版本

## 3.1 版本目标

V1.0.x 阶段不以新增大量用户功能为目标，而是对已经发布的核心能力进行稳定性、隐私准确性、数据可靠性和可维护性收口，为 V1.1-V1.4 提供可靠基础。

当前仓库已经进入 1.0.x 发布阶段，因此不得重写已经存在的历史 Tag。V1.0 阶段剩余工作应继续使用新的 1.0.x 版本号完成，并在里程碑结束时创建新的不可变 Tag。

---

## 3.2 Clipboard Source Capture 一致性

### 功能定位

保证每一条剪贴板历史准确归属于真实来源应用，同时确保应用黑名单不会因为前台应用快速切换而失效。

### 功能说明

一次剪贴板变化开始处理后，只允许捕获一次来源应用信息：

```text
Pasteboard Change
↓
Capture SourceApplicationInfo Once
↓
Privacy Validation
↓
Read Clipboard
↓
Persist History + Capture Event
```

Source App Name、Bundle ID 和 Capture Time 在本次事件生命周期内保持不变。

### 用户场景

用户在 1Password 中复制密码后立即切换到 Chrome。如果 1Password 已被设置为不记录，粘易必须仍然将本次剪贴板事件识别为来自 1Password 并跳过写入，不能因为保存阶段 Chrome 已成为前台应用而错误记录。

### 功能边界

不实现跨进程剪贴板审计、历史来源人工修改或系统级 Clipboard Audit。

### 验收目标

- 文本与图片来源一致。
- 快速切换 App 不改变本次捕获来源。
- Blocked App 内容不会进入数据库。
- Capture Event 与主记录来源一致。

---

## 3.3 Sensitive Detector V2

### 功能定位

降低密码、Token、银行卡等敏感内容被误保存的概率，同时显著减少 Git SHA、Hash、Trace ID、UUID 等开发者常见文本被误判。

### 功能说明

将简单 Boolean 判断升级为结构化检测结果：

```text
SensitiveDetectionResult
├── type
├── confidence
└── reason
```

检测能力至少拆分为：

- CredentialDetector：password、API Key、Access Token、Authorization Header。
- BankCardDetector：格式判断 + Luhn Check。
- IdentityDetector：身份证日期与校验位。
- SecretDetector：高概率 Secret，但不得仅因长字符串直接判定敏感。
- UserRuleDetector：为后续用户自定义隐私规则预留边界。

### 隐私原则

全部检测在本机完成，不允许为了敏感信息判断调用 AI 或网络服务。

### 验收目标

建立独立正反样本测试，至少覆盖 Password、API Token、银行卡、身份证、Git SHA、MD5、UUID、Trace ID、随机长字符串等。

---

## 3.4 Storage Reconciliation

### 功能定位

保证 SQLite 历史数据库和应用管理的图片、缩略图文件长期保持一致。

### 功能说明

新增 `StorageReconciliationService`，安全处理：

- DB 有记录但原图不存在。
- 文件存在但 DB 无记录。
- 原图存在但缩略图缺失。
- 图片损坏。
- 临时文件残留。

安全原则：**宁可暂时保留一个不确定文件，也不能误删有效用户数据。**

### 用户价值

长期运行、异常退出、强制关机、磁盘空间不足或版本升级后，不应持续积累幽灵记录、无效缩略图和孤立文件。

---

## 3.5 Search Task Lifecycle

### 功能定位

保证快速输入搜索关键词时界面稳定，旧搜索永远不能覆盖新搜索。

### 交互流程

```text
User Input
↓
Immediate Local Filter
↓
Cancel Previous Search Task
↓
150ms Debounce
↓
Database Search
↓
Ranking
↓
Only Latest Result Can Commit UI State
```

搜索期间不得清空当前结果、闪白屏、抢焦点或阻塞继续输入。

---

## 3.6 PasteCoordinator

### 功能定位

统一未来 History、Slot、Snippet、Workflow、AI Result、Action Result 的所有复制和直接粘贴行为。

### 功能说明

新增 `PasteCoordinator`，统一负责：

- 写入 Clipboard。
- Automatic Paste 策略判断。
- Accessibility 权限。
- 目标应用激活。
- Command + V 发送。
- Clipboard-only fallback。
- Paste/Reuse Usage 统计。
- 错误处理与提示。

View 与 History ViewModel 不再分别实现完整粘贴流程。

---

## 3.7 ViewModel 架构收敛

### 功能定位

降低后续 Slots、Snippets、Queue、Workflow 继续加入后形成“大 ViewModel”的风险。

### 目标结构

```text
HistoryPanelViewModel
├── HistoryListViewModel
├── SearchViewModel
└── Selection State

PasteCoordinator
ContentActionPanelViewModel
OCRViewModel
```

重构前后 UI、快捷键、搜索、恢复和粘贴行为必须保持一致。

---

## 3.8 SQLite 基础治理

评估并验证 `PRAGMA journal_mode=WAL;`，重点测试 Clipboard 写入与 Search 只读连接并发场景，同时检查 busy timeout、checkpoint 和事务边界。

只有性能和一致性测试证明收益后才能启用 WAL，不以“理论更快”为理由直接切换。

# 4. V1.1 —— 高频内容管理

## 4.1 版本目标

V1.1 开始解决“哪些内容我每天都需要重复使用”的问题，把粘易从历史记录工具推进为高频内容管理工具。

---

## 4.2 Pinned Slots

### 功能定位

提供 1-9 个固定内容槽位，让高频内容不需要再次搜索历史。

### 功能说明

用户可将 History、Snippet 或自定义文本固定到 Slot 1-9，例如：

```text
1 → 测试环境 URL
2 → 邮箱
3 → 常用 SQL
4 → Git 命令
```

主界面增加轻量 Pinned 区域，并支持快捷键直接复制或粘贴。

### 核心交互

历史记录菜单：

```text
固定到槽位
├── 1
├── 2
├── ...
└── 9
```

如果目标槽位已有内容必须确认替换，不能静默覆盖。

### 数据原则

固定槽位不能因为普通历史被清理后立即失效，应保存稳定的内容快照或使用独立持久化模型。

---

## 4.3 Tags

### 功能定位

允许用户对重要内容进行人工分类。

### 功能说明

一条历史可拥有多个 Tag，例如：

```text
#docker
#sql
#api
#work
```

Tag 与 Content Type 独立，支持 `tag:docker` 结构化搜索。

删除 Tag 只删除标签或关联，不删除历史记录。

---

## 4.4 Smart Collections

### 功能定位

把常用搜索条件保存成动态集合，而不是复制数据。

### 功能说明

Smart Collection 保存：

```text
Name
Search Query
```

例如：

```text
Terminal Commands → app:terminal type:shell
Favorite SQL      → type:sql fav:true
API               → tag:api
```

每次进入 Collection 都重新执行查询，新历史满足条件后自动出现。

---

## 4.5 Application Rules

### 功能定位

让不同应用拥有不同的剪贴板记录策略。

### 功能说明

Blocked Apps 升级为 Application Rules。首版至少支持 Record / Don't Record，后续逐步增加 Retention、Preferred Content Type、Temporary、Encrypted 等策略。

建议规则优先级：

```text
Global Pause
>
Application Rule
>
Sensitive Filter
>
Normal Capture
```

设置入口统一放在 Privacy / Application Rules。

---

## 4.6 Search V2 / SQLite FTS5

### 功能定位

解决历史规模增长后固定 500 候选召回上限的问题，使数万甚至十万条历史仍能有效搜索。

### 功能说明

```text
Query Parser
↓
Structured SQL Filters
↓
SQLite FTS5 Recall
↓
Candidate Set
↓
Swift SearchRanker
↓
Final Results
```

SQLite 负责高效召回，Swift 保持当前相关度、时间、使用次数、收藏和来源等最终排序能力。

FTS 必须支持新增、删除、OCR 更新和旧库升级后的索引一致性与重建。

---

# 5. V1.2 —— Developer Clipboard

## 5.1 版本目标

将一次性开发内容转成可长期复用的个人开发资产，形成与普通 Clipboard Manager 的产品差异。

---

## 5.2 Snippet Library

### 功能定位

把重要历史保存为不受普通历史清理策略影响的长期代码/文本片段。

### 功能说明

历史增加“保存为 Snippet”，Snippet 至少包含标题、正文、分类、语言、收藏、标签和更新时间。

典型内容：Docker 命令、Git 操作、Redis 查询、SQL、cURL、Nginx 配置、SSH 命令等。

Snippet 提供独立入口，并支持搜索、编辑、复制、粘贴和删除。

---

## 5.3 Snippet Template

### 功能定位

将固定片段升级成可填写变量的模板。

### 功能说明

首版支持简单变量语法：

```text
{{name}}
```

例如：

```text
ssh {{user}}@{{host}}
```

执行前要求用户填写变量，再生成最终内容。

首版不支持条件、循环、脚本和表达式；变量值默认不保存。

---

## 5.4 Developer Content Types & Actions

新增或增强：

- YAML：Format、Validate、YAML ↔ JSON。
- XML：Pretty Format、Minify、结构校验；禁止远程 DTD/XSLT。
- IP / CIDR：Network、Mask、Broadcast、Host Range、Host Count，首版优先 IPv4。
- Cron：格式校验、可读解释、未来执行时间；明确采用的 Cron 语法标准。
- cURL：Format、Minify、提取 URL/Headers/Method，并转换为 Python requests、Java HttpClient、JavaScript fetch。

所有开发者动作只转换文本，不执行 SQL、Shell 或网络请求。

---

## 5.5 Paste Queue

### 功能定位

解决需要向目标应用按顺序输入多段内容的场景。

### 功能说明

用户可多选内容加入 Queue，并进行 Start、Pause、Clear、Reorder。

```text
A
B
C
↓
Paste Queue
↓
第一次粘贴 A
第二次粘贴 B
第三次粘贴 C
```

队列完成或取消后必须清理 Queue Session，并与 ClipboardMonitor 的内部写入抑制机制正确协作，不能把粘易自己的队列写入再次记录成历史。

---

# 6. V1.3 —— Workflow Automation

## 6.1 版本目标

把当前一次性的 Content Action 连续操作保存为可重复执行的 Workflow，让粘易从 Content Toolkit 进一步进入轻量内容自动化。

---

## 6.2 Workflow Model

Workflow 由有序 Step 构成：

```text
Workflow
├── Name
├── Description
└── Steps
    ├── Step 1 / Action ID
    ├── Step 2 / Action ID
    └── Step N / Action ID
```

每一步输入为上一步输出，第一步输入为用户当前选择的内容。

---

## 6.3 Save Action Chain as Workflow

用户完成：

```text
Base64 Decode
↓
JSON Format
```

后可保存为 `Decode API Payload`，以后对其他记录直接运行。

---

## 6.4 Workflow Engine

新增 `WorkflowExecutor`，按顺序执行受控 ContentAction。

任何一步失败时：

- 立即停止。
- 显示失败步骤。
- 保留上一成功结果。
- 不继续执行后续步骤。
- 允许用户返回修改。

---

## 6.5 Command Palette & Shortcut

`Command + K` 中增加 Workflows 区域，同时允许用户为 Workflow 分配快捷键。

快捷键触发后默认进入结果 Preview，不允许默认直接粘贴，避免自动化误操作。

---

## 6.6 Workflow Import / Export

支持 JSON 导入导出 Workflow，内容仅包含 Workflow Name、Version、Step、Action ID 和安全配置。

严禁包含 Clipboard History、API Key、Token、Secret 或 AI Credential。

导入必须校验 Schema、Unknown Action、Duplicate Workflow 和 Invalid Step。

---

## 6.7 Workflow 安全边界

V1.3 只允许调用粘易内置、受控且可测试的 ContentAction。

明确禁止：

- Shell Execution。
- SQL Execution。
- HTTP Request。
- JavaScript / Python Script。
- Executable Plugin。

---

# 7. V1.4 —— AI & Privacy Platform

## 7.1 版本目标

建立长期可扩展的 AI Provider 层和更完整的本地隐私体系，而不是继续把 AI 能力绑定单一服务商。

---

## 7.2 AIProvider 抽象

统一定义 AI Provider 合约，Provider 负责 Authentication、Endpoint、Model、Request、Response、Usage、Error Mapping。

首批计划支持：

- DeepSeekProvider。
- OpenAICompatibleProvider。
- OllamaProvider。
- CustomProvider。

V1.0.5 已按产品决策将默认 API Key 存储改为 Application Support 下的本地明文凭据文件，以避免重启后访问钥匙串。后续多 Provider 设计必须在“本地文件体验”和“Keychain 级安全”之间提供清晰策略，Endpoint 与 Model 等非密钥配置可继续进入 UserDefaults。

---

## 7.3 OpenAI Compatible & Ollama

OpenAI Compatible Provider 面向 OneAPI、New API、LiteLLM、vLLM API Server、企业内部统一模型网关等场景。

Ollama Provider 提供 Local AI 路径。UI 必须明确区分 `Local` 与 `Remote`，远程 Provider 继续遵守 Remote Processing Consent。

---

## 7.4 AI Actions

计划增加：

- Polish。
- Translate。
- Summarize。
- Explain。
- Explain Error。
- Generate Commit Message。
- Generate Regex。
- Explain SQL。
- Explain Shell。

AI Action 只能读取用户当前明确选择的内容。禁止后台自动上传 Clipboard、整个历史数据库、图片或无关记录。

---

## 7.5 Privacy Vault

### 功能定位

为高安全需求用户提供独立加密历史区域。

### 功能说明

Privacy Vault 必须同时考虑 Text、OCR Text、Image、Thumbnail、Derived Content，不能只加密 SQLite 正文而留下明文图片。

密钥使用 macOS Keychain 管理；具体加密格式、密钥生命周期和恢复策略必须在编码前另行完成 Threat Model 与安全设计评审。

---

## 7.6 Touch ID / Local Authentication

Privacy Vault 可要求 LocalAuthentication。认证失败或取消时不得展示 Vault 内容。

---

## 7.7 Temporary History & Temporary Record

支持暂停记录：5 分钟、30 分钟、1 小时、直到明天，到期自动恢复，并在菜单栏明显显示 Recording Paused。

记录可设置 5 分钟、30 分钟、1 小时、Until Quit 等生命周期，到期后同步删除数据库、原图和缩略图。

推荐首版规则：Temporary Record 不允许固定到 Slot 或保存为 Snippet，避免生命周期冲突。

---

## 7.8 Capture Policy

随着 Pause、Blocked App、Sensitive、Temporary、Encrypted 等规则增加，统一收敛到 `CapturePolicyEvaluator`：

```text
Clipboard Event
↓
Source App
↓
CapturePolicyEvaluator
↓
Skip / Normal / Temporary / Encrypted
↓
Persist
```

ClipboardMonitor 不再继续堆叠业务条件判断。

---

## 7.9 Backup / Restore

用户主动导出本地 Backup Package，用于换机和手动备份。

计划包含：普通历史、图片、Snippet、Tags、Slots、Collections、Workflows 和可安全迁移的设置。

默认禁止备份 AI API Key、本地 AI 凭据文件、Keychain Secret、Authentication Credential。Privacy Vault 是否包含在备份中必须由单独安全方案决定。

---

# 8. Git Tag 与 Release 策略

## 8.1 Tag 原则

每个版本里程碑必须创建独立、不可变 Tag。已经存在的历史 Tag 不允许删除、移动或覆盖。

推荐使用语义化版本：

```text
v1.0.x   当前 1.0 稳定阶段继续递增
v1.1.0
v1.2.0
v1.3.0
v1.4.0
```

如果某个主里程碑需要修复版本，则使用 `v1.1.1`、`v1.1.2` 等继续递增。

## 8.2 Tag 门禁

只有同时满足以下条件才允许创建 Tag：

```text
代码完成
+
定向测试通过
+
完整测试通过
+
Build 验证通过
+
数据库 Migration 验证通过
+
文档同步完成
+
CHANGELOG 完成
+
三语言完成
+
隐私/日志安全检查完成
+
工作区状态确认
```

## 8.3 Tag ≠ Release

创建 Tag 后，本版本开发任务立即停止。

当前开发任务禁止继续执行：

- 正式 Release Archive。
- Developer ID Distribution。
- Notarization。
- Sparkle Release Package。
- GitHub Release。
- 正式 appcast 发布。
- App Store 上传。
- DMG/PKG 正式发布。

这些动作统一由后续独立 Release Task 基于已经确认的 Tag 执行。

完整生命周期：

```text
Version Development
↓
Tests / Build / Docs / Review
↓
Create Tag
↓
Push Tag
↓
STOP

后续独立任务：
Tag
↓
Release Archive
↓
Signing
↓
Notarization
↓
Release Verification
↓
Sparkle Package
↓
GitHub Release
↓
Appcast
```

# 9. Codex 长期开发规则

Codex 执行本规划时必须遵守：

1. 一次只执行当前版本中的一个 Task。
2. 不得跨版本提前开发后续能力。
3. 每个 Task 使用 LOOP：Locate → Outline → Operate → Prove。
4. 测试先行：先观察目标测试失败，再实现最小功能并验证通过。
5. 数据库变化只能通过递增 Migration 完成，禁止修改已经发布的 Migration。
6. 用户可见功能必须同步 English、简体中文、繁体中文。
7. 核心代码变化必须同步开发文档。
8. 用户功能变化必须同步 README / User Guide / CHANGELOG 中适用文档。
9. 隐私行为变化必须更新 Privacy Policy。
10. 禁止在日志中记录完整 Clipboard、JWT、OCR 全文、AI Prompt/Response、Token 或 API Key。
11. Remote AI 只能由用户明确触发，不能因为复制、搜索、选中或打开历史自动发送数据。
12. 不得自行实现 Shell Execution、SQL Execution、HTTP Workflow、脚本插件、云同步、账号系统等未进入规划的能力。
13. 一个功能完成后形成独立、可审查 Commit。
14. 一个版本完成后创建版本 Tag 并停止；正式 Release 留给后续任务。
