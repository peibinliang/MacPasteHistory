# 粘易 V1.0.1 敏感内容控制与自动更新设计

## 背景

V1.0.0 的剪贴板监听会在保存文本前执行敏感内容检测。用户提供的两个失败样例并非超过长度限制：cURL 样例命中 `Bearer` 和长令牌规则，钉钉文档样例中的 `access_token=xxxxx` 命中访问令牌规则，因此都被静默跳过。

V1.0.1 需要让用户在理解风险后关闭敏感内容过滤，同时增加版本信息模块，并通过 GitHub Releases 向已经安装的应用推送可直接安装的更新。

## 目标

- 将版本升级为 `1.0.1`，构建号升级为 `2`。
- 保持敏感内容过滤默认开启，并允许用户在设置中关闭。
- 关闭过滤后，完整记录包含 cURL、Token、URL、多行内容和 Emoji 的文本。
- 在设置中提供独立的“关于与更新”页面。
- 定期自动检查 GitHub Releases 上的新版本，并提供手动检查入口。
- 支持在应用内下载、验证、安装并重新启动，而不是要求用户手工覆盖应用包。
- 更新失败不得影响剪贴板监听、历史数据或当前已安装版本。

## 非目标

- 不实现云同步、账号系统、更新渠道分组或强制更新。
- 不自行实现安装器、二进制替换、增量补丁或签名算法。
- 不通过 GitHub API 自行解析“最新版本”。
- 不改变现有敏感内容识别规则；本次仅增加用户可控的启停能力。
- 不改变历史数据库结构和存储位置。

## 方案选择

### 采用方案：Sparkle 2 + GitHub Releases

通过 Swift Package Manager 集成 Sparkle 2。GitHub Release 托管经过签名和公证的更新 ZIP，GitHub Pages 上的 `https://peibinliang.github.io/MacPasteHistory/appcast.xml` 提供版本、发布说明、下载地址和 EdDSA 签名。应用使用 Sparkle 的标准更新控制器执行周期检查、手动检查、下载、验证、替换和重启。

该方案复用成熟的 macOS 更新安全边界，避免自行实现高风险的进程替换、权限提升和失败回滚逻辑。

### 未采用方案

- 自研 GitHub 更新器：需要自行实现版本比较、下载、签名校验、退出、替换、授权和回滚，安全与维护成本过高。
- 仅提示并打开 GitHub Release：仍要求用户手工下载和覆盖应用，不满足应用内更新目标。

## 架构设计

### 敏感内容过滤设置

`UserDefaultsConfig` 增加布尔字段 `filterSensitiveContent`，默认值为 `true`。现有安装升级后没有该键时仍使用默认值，因此不会降低既有用户的隐私保护。

`SettingsViewModel` 暴露此设置并负责持久化。“隐私”页面增加“过滤敏感内容”开关和简短说明。用户首次尝试关闭时显示确认提示，明确密码、Token、身份信息等内容可能保存到本地未加密数据库。用户取消时开关保持开启。

`ClipboardMonitor` 在每次文本捕获时读取最新设置。过滤开启时继续调用 `SensitiveContentDetector`；过滤关闭时跳过敏感检测并执行现有保存流程。设置值不得只在监听器初始化时缓存，以确保用户更改后立即生效。

文本仍通过 `ClipboardReader` 做现有的控制字符清理和首尾空白裁剪，但不截断正文，不改变内部换行、引号、URL、中文或 Emoji。

### 版本信息

增加 `AppVersionProviding` 协议及 Bundle 驱动的默认实现，由设置页注入并统一读取：

- `CFBundleShortVersionString`
- `CFBundleVersion`
- 应用显示名称

设置页新增“关于与更新”分类，显示应用图标、名称、版本与构建号、自动检查状态、“检查更新”按钮和 GitHub 项目链接。版本信息必须来自运行中的 Bundle，界面不得写死 `1.0.1`。

### 更新服务

增加 `UpdateService`，封装 Sparkle 的标准更新控制器，并向 SwiftUI 暴露最小状态：

- 是否允许执行手动检查
- 是否正在检查
- 自动检查是否启用
- 最近一次需要在设置页展示的错误或状态

`AppDelegate` 创建单一 `UpdateService` 实例并注入设置页，避免多个 Sparkle 控制器同时管理同一应用。`SparkleUpdateDriver` 把发现更新、无更新和异常终止的 delegate 事件转为设置页状态；手动检查期间按钮禁用。自动检查由 Sparkle 的标准调度负责，且不降低 `SUEnableAutomaticChecks`。由于应用默认为 `LSUIElement`，driver 声明 gentle scheduled reminder 能力，在更新会话内临时显示并标记 Dock 图标，用户关注或会话结束后清理，同时保留用户的 Dock 显示偏好。Sparkle 标准 UI 继续负责下载、验证、安装、取消和重启的完整交互。

应用不直接调用 GitHub Releases API。`SUFeedURL` 指向 `https://peibinliang.github.io/MacPasteHistory/appcast.xml`，appcast 中的 enclosure URL 指向对应 GitHub Release 的签名 ZIP。

### 沙盒与网络

应用继续启用 App Sandbox。集成 Sparkle 时按其沙盒指南启用 Installer Launcher XPC、Downloader XPC 及所需 Mach lookup 例外。主应用继续保持 `com.apple.security.network.client` 为 `false`，由 Downloader XPC 获取 appcast、纯文本或 Markdown 发布说明及更新包，避免扩大整个剪贴板应用的网络权限。该配置必须由 Release 构建和真实升级测试证明可用，并同步到 entitlement 校验脚本。

## 数据流

### 文本捕获

1. `ClipboardMonitor` 检测到 pasteboard change count 变化。
2. 依次执行内部恢复跳过、暂停记录、来源应用黑名单和内容类型开关检查。
3. `ClipboardReader` 读取并清理文本。
4. 读取当前 `filterSensitiveContent`：
   - 开启且命中敏感规则：不保存，也不记录剪贴板正文到日志。
   - 关闭：跳过敏感规则。
5. 完整文本进入现有分类、去重和数据库保存流程。
6. 发布历史变更通知刷新界面。

### 更新检查与安装

1. Sparkle 按用户设置和标准周期请求固定 appcast URL。
2. Sparkle 比较 appcast 构建号与当前 `CFBundleVersion`。
3. 发现更新时展示标准更新界面、版本和发布说明。
4. 用户确认后下载 GitHub Release ZIP。
5. Sparkle 验证 HTTPS 来源、EdDSA 签名和应用代码签名。
6. 验证通过后退出应用、原子替换应用包并重新启动。
7. Application Support 数据库和 UserDefaults 位于应用包外，因此升级后继续保留。

## 交互设计

### 隐私设置

- 开关标题：“过滤敏感内容”。
- 默认状态：开启。
- 辅助说明：开启时不会记录检测到的密码、Token、身份信息等内容。
- 关闭确认：说明历史数据库当前未加密，关闭后敏感信息可能保存在本机。
- 确认关闭后立即生效；重新开启无需二次确认。

### 关于与更新

- 页面标题：“关于与更新”。
- 显示格式：`版本 1.0.1（构建 2）`，实际值来自 Bundle。
- 提供自动检查更新状态或开关，默认启用定期检查。
- “检查更新”按钮在检查进行中禁用，避免并发请求。
- GitHub 链接指向 `https://github.com/peibinliang/MacPasteHistory`。

### 更新结果

- 有更新：显示 Sparkle 标准更新窗口，允许查看发布说明、下载并安装。
- 已是最新版：手动检查必须明确反馈当前已是最新版本。
- 网络或 appcast 错误：显示可理解的错误；剪贴板监听继续运行。
- 用户取消下载、授权或安装：保留当前版本，不修改历史数据。
- 签名或代码签名验证失败：拒绝安装并保留当前版本。

## 发布与安全设计

- 正式更新包必须使用 Developer ID 签名并完成 Apple 公证。
- 更新 ZIP 必须使用 Sparkle EdDSA 密钥签名。
- EdDSA 私钥只保存在发布者本机钥匙串或受保护的发布环境，不提交 Git、GitHub Release、appcast 或 CI 日志。
- 应用 Bundle 仅包含公钥。
- GitHub Release `v1.0.1` 至少包含签名 ZIP、校验文件和发布说明。
- GitHub Pages 地址 `https://peibinliang.github.io/MacPasteHistory/appcast.xml` 必须始终返回合法 XML；发布顺序应避免 appcast 指向尚未上传的资源。
- `CFBundleVersion` 使用单调递增整数；V1.0.1 使用构建号 `2`。

## 发布流程

1. 更新版本、构建号、CHANGELOG、用户指南、隐私说明和发布指南。
2. 生成 Xcode 项目并执行单元测试、Release 构建和现有静态校验。
3. 使用 Developer ID 对 Release 应用签名并完成 Apple 公证。
4. 打包保留符号链接和权限的 ZIP。
5. 使用 Sparkle 工具生成 EdDSA 签名与 appcast。
6. 创建 GitHub Release `v1.0.1`，上传 ZIP、校验文件和发布说明。
7. 将 appcast 发布到 GitHub Pages 固定地址；确认 enclosure URL 可下载已上传的 ZIP。
8. 从真实安装的 V1.0.0 触发自动和手动检查，完成端到端升级。
9. 验证应用重启为 V1.0.1，历史数据库、收藏、设置和快捷键均保留。
10. 完成支持系统版本上的人工 Release QA 后再对外发布。

## 测试设计

### 单元测试

- 新配置在没有持久化值时默认为开启。
- 过滤开关可持久化，并由 `SettingsViewModel` 正确加载和更新。
- 用户取消关闭确认时配置保持开启。
- 过滤开启时，现有密码、Token、证件号和银行卡模式继续被跳过。
- 过滤关闭时，用户提供的 cURL 样例完整保存。
- 过滤关闭时，用户提供的钉钉长文本样例完整保存。
- 不包含敏感模式的普通长文本在过滤开启时也能保存，防止把长度误认为过滤条件。
- 保存后的文本保留内部换行、引号、URL、中文和 Emoji。
- 版本信息从注入的 Bundle/Provider 读取。
- “检查更新”按钮调用注入的更新服务，并在检查中禁用。

测试夹具不得包含用户提供的真实 Bearer Token；使用明确标记为测试用途的合成令牌，但保持足以命中检测规则的结构。

### 集成与发布验证

- XcodeGen 生成项目后，Sparkle 产品和嵌入关系正确。
- Release app 包含所需 Sparkle framework/XPC 服务和正确 entitlement。
- appcast XML 可解析，版本为 `1.0.1`，构建号为 `2`，下载地址使用 HTTPS。
- appcast enclosure 签名能验证对应 ZIP，ZIP 内 Bundle 版本与 appcast 一致。
- 模拟不可用网络、404、损坏 appcast 和无效签名时不会破坏当前安装。
- 在真实安装的 V1.0.0 上验证手动检查、自动检查提示、下载、退出、替换和重启。
- 升级前后的历史记录数、收藏、设置和快捷键一致。
- 在 Apple Silicon 和项目支持的 macOS 版本上完成现有 Release QA；Intel 是否继续作为发布门禁遵循现有发布矩阵与明确记录的发布决定。

## 文档与 OpenSpec

实施时新增一个 V1.0.1 OpenSpec change，描述：

- 用户可控制敏感内容过滤且默认安全。
- 设置页显示运行时版本信息。
- 应用可以从 GitHub Releases 安全检查并安装更新。
- 发布产物、appcast、签名和端到端升级均有可复核证据。

同时更新：

- `docs/changelog/CHANGELOG.md`
- 中英文 README 或用户指南中的隐私行为与更新说明
- `docs/privacy-policy.md`
- `docs/release/RELEASE_PREP_GUIDE.md`
- 版本、签名、entitlement 和 Release readiness 校验脚本

## 验收标准

- V1.0.1 显示版本 `1.0.1 (2)`。
- 默认设置下仍跳过检测到的敏感文本。
- 用户确认关闭过滤后，两段回归样例都能完整进入历史并正常搜索、查看和恢复。
- 普通长文本不会因长度被跳过。
- “关于与更新”页可查看版本并手动检查更新。
- 自动检查能发现发布到 GitHub Releases 的更高构建号。
- V1.0.0 能在应用内升级到 V1.0.1，无需用户覆盖 `.app`。
- 无效或被篡改的更新包不会安装。
- 升级失败或取消后 V1.0.0 仍可运行，历史数据不丢失。
- 升级成功后 V1.0.1 能正常监听剪贴板，原有历史和设置保持不变。
